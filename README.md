# Frontend Job Finder

Локальное монорепо для сбора frontend-вакансий с карьерных страниц компаний и
просмотра результатов в React-админке. Репозиторий не содержит пользовательские
списки компаний, результаты поисков или резюме — каждый пользователь загружает
свои данные локально.

Приложение не отправляет отклики, не обходит CAPTCHA и anti-bot защиту, не требует
AI или платных API. Рабочие данные хранятся локально в SQLite; JSON-файлы
остаются совместимым экспортом для диагностики и первоначального импорта.

## Структура

```text
job-finder/
├── backend/                 # Python crawler, FastAPI, данные, тесты и snapshots
│   ├── data/                  # создаётся/заполняется локально
│   ├── output/                # SQLite, JSON-экспорт и логи; исключены из Git
│   ├── src/job_finder/
│   └── tests/
├── frontend/                # React + TypeScript + Vite + Tailwind
│   └── src/
├── .gitignore
└── README.md
```

## Требования

- Python 3.12 или новее (Python 3.13 полностью поддерживается);
- Node.js 20.19+ или 22.12+;
- Windows PowerShell для команд ниже.

## Первый запуск

После однократной установки зависимостей backend и frontend всё приложение можно запускать одной командой из корня проекта:

```powershell
.\start-job-finder.cmd
```

Команда работает и при системном запрете прямого запуска `.ps1`. Скрипт не создаёт второй процесс, если backend или frontend уже запущен, ожидает их готовности и открывает `http://127.0.0.1:5173`. Логи сохраняются в `.logs/`. Чтобы не открывать браузер, передайте `-NoBrowser`.

Управление запущенным приложением выполняется из корня проекта:

```powershell
.\start-job-finder.cmd                 # запустить отсутствующие процессы
.\status-job-finder.cmd                # показать состояние, порты и PID
.\stop-job-finder.cmd                  # остановить frontend и backend
.\restart-job-finder.cmd               # остановить и запустить заново
.\restart-job-finder.cmd -NoBrowser    # перезапустить без открытия браузера
```

`stop` проверяет, что процессы на портах 5173 и 8000 действительно похожи на Job Finder. Если порт занят зависшим процессом и обычная проверка невозможна, можно осознанно выполнить `.\stop-job-finder.cmd -Force` или `.\restart-job-finder.cmd -Force`.

### 1. Backend

```powershell
Set-Location backend
py -V:3.13 -m venv .venv
.\.venv\Scripts\Activate.ps1
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m playwright install chromium
.\.venv\Scripts\python.exe -m job_finder serve
```

Если в приглашении PowerShell уже отображается `(.venv)`, сначала выполните
`deactivate`, чтобы не смешивать старое корневое окружение с новым
`backend/.venv`. Тег после `-V:` берётся из `py --list`; на вашей машине это
`3.13`.

API будет доступен на `http://127.0.0.1:8000`, документация — на
`http://127.0.0.1:8000/docs`. Используется один Uvicorn worker.

### 2. Frontend

В новом окне PowerShell:

```powershell
Set-Location frontend
npm.cmd install
npm.cmd run dev
```

Откройте `http://127.0.0.1:5173`. Vite проксирует запросы `/api` в локальный
backend.

### 3. Добавление собственных компаний

После чистого клона список компаний пуст. Откройте раздел «Компании», нажмите
«Добавить новые компании» и загрузите свой XLSX. Компании сохранятся в
`backend/output/job_finder.db`; `backend/data/companies.json` останется локальным
совместимым экспортом. Формат JSON
можно посмотреть в `backend/data/companies.example.json`; сам файл-пример
приложением не используется.

## Использование

На странице «Текущий поиск» кнопка «Найти вакансии» запускает обход всех включённых
компаний текущего пользователя из SQLite. Кнопка «Обработать новые компании» обрабатывает компании, которых ещё нет в последнем отчёте. Кнопка «Обновить вакансии» проверяет только включённые компании без предыдущей проверки или с `last_crawled_at` старше 24 часов. На странице «Компании» можно запустить поиск только для выбранных строк и увидеть дату последней проверки. Во время запуска показываются прогресс,
число обработанных компаний и найденных вакансий. Второй одновременный запуск через
UI, API или CLI блокируется.

После успешного завершения:

1. новый отчёт атомарно становится текущим запуском в SQLite;
2. JSON-снимки сохраняются как совместимый диагностический экспорт;
3. хранятся текущий и три предыдущих запуска;
4. ошибка отдельной компании остаётся частью валидного результата;
5. катастрофическая ошибка не заменяет предыдущий `latest.json`.

История показывает до трёх предыдущих запусков, не включая текущий. Одинаковая
вакансия в разных snapshots допустима: каждый snapshot — отдельный поиск.

## CLI

После установки backend команды можно выполнять из любой директории: пути по
умолчанию вычисляются от папки `backend`.

```powershell
# Все компании из текущего companies.json
.\backend\.venv\Scripts\python.exe -m job_finder crawl

# Изменить параллелизм
.\backend\.venv\Scripts\python.exe -m job_finder crawl --concurrency 8

# Импортировать собственный Excel
.\backend\.venv\Scripts\python.exe -m job_finder import-xlsx `
  C:\path\to\your_companies.xlsx
```

Для HTTP/Playwright действуют отдельные timeout и retry, ограничение запросов на
домен и общий watchdog компании. Обычные карьерные страницы обходятся по
`rel=next`, Next/«Следующая» и нумерованной пагинации. Playwright fallback также
нажимает `Load more` и выполняет ограниченный infinite scroll. Защита от циклов
останавливает обход после 20 страниц, 20 браузерных взаимодействий или 500 сырых
вакансий на компанию и записывает причину остановки в `warnings`. `Ctrl+C`
корректно закрывает ресурсы.

## API

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `POST` | `/api/crawls` | Запустить полный поиск, ответ `202` |
| `GET` | `/api/crawls/status` | Статус и прогресс текущего запуска |
| `GET` | `/api/companies` | Текущий список компаний с сайтами, локациями и crawl-статусом |
| `POST` | `/api/companies/import` | Импортировать XLSX с объединением, дедупликацией или заменой списка |
| `GET` | `/api/runs/latest` | Текущий полный отчёт |
| `GET` | `/api/runs/history?limit=3` | До трёх предыдущих запусков |
| `GET` | `/api/runs/{run_id}` | Полный исторический snapshot |
| `GET` | `/api/health` | Проверка backend |
| `POST` | `/api/auth/register` | Создать аккаунт и начать cookie-сессию |
| `POST` | `/api/auth/login` | Войти по email и паролю |
| `POST` | `/api/auth/logout` | Завершить текущую сессию |
| `GET` | `/api/auth/me` | Получить текущего пользователя |

Backend слушает только `127.0.0.1` и требует авторизацию. Пароли хешируются
Argon2, а сессия хранится в постоянной таблице и передаётся через `HttpOnly`
cookie. JavaScript не имеет доступа к токену сессии.

При первой регистрации существующие локальные компании, запуски и резюме
переходят созданному аккаунту без копирования данных. Следующие аккаунты получают
собственные пустые списки. Выйти можно кнопкой внизу бокового меню.

## SQLite и миграции

При первом запуске существующие `companies.json`, `latest.json`, snapshots и
индекс резюме автоматически импортируются в `backend/output/job_finder.db`.
Если база уже содержит данные, повторный запуск не перезаписывает их старыми JSON.

```powershell
Set-Location backend
.\.venv\Scripts\python.exe -m job_finder db-upgrade
.\.venv\Scripts\python.exe -m job_finder db-info
```

Схема управляется Alembic и использует универсальные типы SQLAlchemy. URL базы
задаётся через `DATABASE_URL`. Для будущего PostgreSQL потребуется установить
`.[postgres]`, применить миграции и перенести записи; API и crawler менять не
потребуется.

## Дедупликация и совместимость

Новые отчёты имеют `schema_version: "2.0"`, `source_job_id` и `work_format` со
значениями `remote`, `hybrid`, `onsite` или `unknown`. Старые snapshots версии 1.0
читаются без изменения исходных файлов.

`job_id` строится из компании, источника и ATS ID; если ID отсутствует — из
канонического URL. Tracking-параметры, fragment, регистр host и завершающий `/`
нормализуются. Разные ATS requisitions с разными ID не объединяются, даже если у
них совпадают название и локация.

## Фильтры и тема

Интерфейс фильтрует вакансии по title, нескольким технологиям с OR-логикой,
локации Armenia/Yerevan/Երևան и формату работы. Таблица использует клиентскую
пагинацию по 20 строк. Те же фильтры работают для исторических запусков.

## Резюме и совпадение с вакансиями

В разделе «Аккаунт» можно локально хранить до трёх PDF-резюме на русском или английском языке и выбрать одно активное. Размер одного файла ограничен 5 МБ. Сканированные PDF без текстового слоя требуют OCR и пока не поддерживаются.

Для активного резюме backend извлекает технологии, роль и seniority, после чего рассчитывает для каждой вакансии объяснимую оценку от 0 до 100. Чекбокс «Матч с активным резюме» оставляет результаты с оценкой от 35% и сортирует их по убыванию совпадения. Внешний AI и передача резюме сторонним сервисам не используются. PDF сохраняются только в `backend/data/resumes/`, а метаданные и извлечённый текст — в SQLite для текущего пользователя.

Палитра меняется в одном месте — `frontend/src/styles.css`:

```css
:root {
  --app-bg: #F3F4F4;
  --app-dark: #2C2C2C;
  --app-primary: #853953;
  --app-primary-dark: #612D53;
}
```

## Настройки backend

При необходимости можно задать переменные окружения:

- `JOB_FINDER_COMPANIES_FILE` — путь к JSON компаний;
- `JOB_FINDER_OUTPUT_DIR` — каталог результатов;
- `JOB_FINDER_RESUMES_DIR` — каталог локального хранения резюме;
- `JOB_FINDER_CONCURRENCY` — число одновременно обрабатываемых компаний;
- `JOB_FINDER_REFRESH_AFTER_HOURS` — через сколько часов компания снова попадает в «Обновить вакансии» (по умолчанию `24`);
- `JOB_FINDER_ALLOWED_ORIGINS` — разрешённые CORS origins через запятую.
